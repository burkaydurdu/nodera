# Phase 5: Mail — Sending domains, Packages, sending over API and SMTP, logs and Webhooks

Vocabulary: `contexts/mail/CONTEXT.md` (Mail, Sending domain, Message, Message event, Webhook,
Suppression, Package, Daily limit, Pause), `contexts/customer/CONTEXT.md` (App, API key, Project,
Role, Permission), `contexts/billing/CONTEXT.md` (Period, Invoice, Invoice line, Threshold, Billing
status, Dunning). Decisions already recorded: ADR-0001 (outbox), ADR-0004 (read models from events),
ADR-0005 (Roles in the token), ADR-0007 (live updates), ADR-0008 (who is told), ADR-0009 (Mail
delivers from its own MTA), ADR-0010 (integration gateway and Project API keys), ADR-0011 (Mail
serves its own DNS zone for DKIM keys).

## Problem Statement

A Team that runs software on Nodera has to send email from it: sign-up codes, password resets,
receipts, alerts. Today it must open an account with a sending service such as SendGrid or Mailgun,
prove its domain there, keep a second dashboard, a second card and a second bill, and live with that
service's rules for small senders. Nodera wants to be that sending service itself: a second product,
Mail, delivered from Nodera's own mail servers, configured inside the Nodera web app as an App of its
own, and charged on the same monthly Invoice as the Team's Droplets.

## Solution

Inside a Project, a Team opens the Mail App, chooses a Package (5,000 to 100,000 emails a month),
adds a Sending domain with the three CNAME records Nodera shows, and creates an API key that may
send. Its software then sends over Nodera's HTTP API, or over SMTP with the API key as the password.
Nodera delivers from its own MTA (KumoMTA on Cherry Servers), signs every Message with the Project's
own DKIM key and handles bounces and complaints itself.

The Team sees every Message and what happened to it for 30 days, receives Message events on up to
three signed Webhooks, and is told when a domain is verified or lost, when its Package is nearly or
fully used, and when its sending is at risk or Paused. Nodera protects its shared IPs with a Daily
limit that grows with clean sending, per-Project Suppressions and an automatic Pause on high bounce
or complaint rates. The Package's price lands on the Team's Invoice: the largest Package a Project
held in a Period is what it pays for that Period.

## Implementation Decisions

### The mail context

- A new bounded context, `mail`, with its own PostgreSQL database, its own Mongo outbox and its own
  consumers, following the droplet context's layering: `api/v1` binds and validates, the application
  handlers hold the rules, aggregates own the model, requests, errors, a thin service and the pgx
  repository.
- One binary with the commands `server` (the management API for the web app, the sending API for the
  integration gateway and an internal API for the MTA, on separate listeners), `smtp` (the relay),
  `dns` (the zone of ADR-0011), `worker` (consumers and jobs under Redis locks), `outbox`, `migrate`,
  `rollback`, `seed`, `seed-rollback` and the operator command `unpause`.
- Aggregates: `access` (Project access with each Project's name), `billing` (Billing status),
  `domain` (Sending domains and their DKIM keys), `packages` (the Package catalog, each Project's
  Package and its Periods), `message` (Messages, recipients, Message events and the delivery spool),
  `suppression`, `limits` (daily counters, the Daily limit, rates and the Pause), `webhook`
  (Webhooks and their deliveries). No aggregate imports a sibling.
- Jobs, each on its own interval and lock: domain checks, key rotation, Period rollover, spool
  dispatch, Daily limit evaluation, rate and Pause evaluation, Webhook delivery, log expiry.

### Project access, Project names and Billing status

- The same event-fed read models as the droplet context (ADR-0004): memberships are last-writer-wins
  on the event's own time with tombstones for removals; a Team never heard of has no payment method.
- The customer context's `ProjectCreated` gains the Project's `name`, and its replay command
  republishes it, so that mail can name the Project on Invoice lines and Notifications without ever
  asking the customer context.
- `TeamBillingStatusChanged` feeds the Billing status. `TeamDropletsDeletionRequested` (day 21 of
  Dunning) ends every Package of the Team.

### Sending domains

- A name is normalized (lower case, IDNA to ASCII, no trailing dot) and must have at least two
  labels, at most 253 characters, valid labels, no IP literal and no name inside Nodera's own zone. A
  Project holds at most 10, each name once; the same name may live in other Projects.
- Each Sending domain gets a random token of eight lower-case alphanumerics, unique platform-wide.
  The Team adds three CNAMEs:
  - return path: `n<token>.<domain>` → `rp.<zone>`
  - DKIM: `n<token>a._domainkey.<domain>` → `a.<token>.dkim.<zone>`
  - DKIM: `n<token>b._domainkey.<domain>` → `b.<token>.dkim.<zone>`

  The token makes every record Project-specific, so another Project's existing records never verify
  this one, and two Projects can verify the same domain.
- Two RSA-2048 key pairs, one per selector, are generated on creation. Private keys are encrypted at
  rest with AES-256-GCM under a key from configuration; selector `a` signs first.
- Statuses: `pending` → `verified` when all three CNAMEs resolve to their targets; `verified` →
  `unverified` when a later check misses one; `unverified` → `verified` when they are back. Each
  record's last check result is kept for the screen. A DMARC record is looked up on the domain and on
  its organizational domain; its absence is a warning, never a refusal.
- Pending domains are checked every 10 minutes during their first 72 hours and daily after; verified
  and unverified ones daily. A check DNS does not answer (a timeout, a SERVFAIL) changes nothing and
  is tried again 10 minutes later; only a record DNS says is missing unverifies. "Verify now" checks
  at once, at most once a minute per domain. Each
  transition to `verified` publishes `MailDomainVerified`; `verified` → `unverified` publishes
  `MailDomainUnverified`; both also publish a realtime message.
- Rotation every 180 days for a verified domain: a fresh key replaces the idle selector's, is
  published at once, and starts signing 48 hours later; the previous key stays published until the
  next rotation.
- Deleting a domain stops sending from it at once; its Messages' logs remain until they expire.

### The DNS zone (ADR-0011)

- `mail dns` answers authoritatively for the configured zone, over UDP and TCP: SOA and NS at the
  apex, MX and SPF TXT for `rp.<zone>`, the configured A/AAAA records of the listener hosts, and the
  DKIM TXT (`v=DKIM1; k=rsa; p=…`) of every key under `a|b.<token>.dkim.<zone>`. Anything else in the
  zone is NXDOMAIN; names outside it are refused.
- Keys come from the mail database through an in-process cache refreshed every 30 seconds, with a
  lookup on a miss. DKIM records carry a 300-second TTL, the static ones 3600.

### Packages and Periods

- The catalog is a seeded table: `5k` 5,000 for $5, `10k` 10,000 for $9, `25k` 25,000 for $19,
  `50k` 50,000 for $29, `100k` 100,000 for $49, in USD per month excluding tax, `numeric` in the
  database and `decimal` in Go.
- A Project's Package copies the catalog price when it is chosen, like a Droplet's Locked price; a
  smaller Package scheduled for the next Period copies its terms when it is scheduled. Choosing needs
  `mail.write`, and every choice of a Package (starting, upgrading, scheduling a smaller one, undoing
  a scheduled change) an `active` Billing status (402 without a payment method, 423 when suspended);
  a cancellation spends nothing and is always allowed.
- An upgrade (more emails) takes effect at once: the Period's allowance becomes the new Package's and
  the used count carries over. A downgrade or a cancellation is scheduled for the next Period and can
  be undone until then by choosing the current Package again.
- One Period row per Project and calendar month (UTC) holds the allowance and the used count. The
  rollover job, idempotent and run every 15 minutes, applies scheduled changes at the boundary
  instant and opens the new Period with nothing used.
- One "email" is one recipient of an accepted Message. Crossing 80% of the allowance publishes
  `MailPackageNearLimit` once per Period; reaching it publishes `MailPackageExhausted` once per
  Period, and sending then stops until an upgrade or the next Period. An upgrade that lifts the
  allowance above a mark re-arms it, so a Project that outgrows its new allowance is told again. A
  Message with more recipients than the Period has left is refused with how many are left (429), so
  a smaller one still goes.
- Billing learns Packages as intervals, like Droplet hours: `MailPackageStarted` (Project, Team,
  Project name, Package code, monthly emails, monthly price as a two-decimal string, start) and
  `MailPackageStopped` (Project, Team, the start of the interval it closes, stop). An upgrade is a
  stop and a start at the same instant; a scheduled change applies at the Period boundary; day 21 of
  Dunning stops every interval of the Team, after applying a change its Period boundary already owed.

### Sending

- One send path serves HTTP and SMTP, checking in this order:
  1. the API key: valid, not revoked, holding `mail.send`; it names the Project;
  2. the request: the sender's address on a `verified` Sending domain of that Project, 1 to 50
     recipients across to, cc and bcc (deduplicated), a subject, text or HTML, at most 10 MB once
     decoded, at most 10 tags of at most 64 characters, custom headers outside a reserved list;
  3. the `Idempotency-Key`, when present (HTTP only, up to 128 characters): a repeat within 24 hours
     answers the first Message without sending;
  4. the Billing status: `suspended` refuses;
  5. the Package: none refuses;
  6. the Pause: Paused refuses;
  7. Suppressions: suppressed recipients are dropped and recorded as `suppressed`;
  8. the limits: the remaining recipients must fit both the Period's allowance and today's Daily
     limit, checked and counted atomically in that order; otherwise the whole Message is refused.
- An accepted Message is stored with its recipients, an `accepted` Message event each, and its MIME
  content in a spool table, then committed. It is handed to the MTA right after the commit, each
  Message in a transaction of its own; a dispatcher job retries what was not handed over, a copy the
  MTA refused included (as while it cannot fetch a signing key), and the spooled content is deleted
  as soon as the MTA holds every copy. Bodies are never kept after that. A recipient still not handed
  over after 24 hours is bounced, as an MTA expires what it cannot deliver; that bounce is Nodera's
  and neither suppresses nor counts against the Project.
- Refusals: no Package 402; Daily limit or Package exhausted 429 with Retry-After (the next UTC
  midnight or the next Period); Paused 423; suspended 423; validation 400; sender not on a verified
  Sending domain 422.
- HTTP contract, `POST /v1/mail/messages` with `Authorization: Bearer <API key>`:
  `from` (address, optional name), `to`, `cc`, `bcc` (address and optional name each), `reply_to`,
  `subject`, `text`, `html`, `attachments` (filename, content type, base64 content, optional
  content id for inline parts), `headers` (name → value), `tags`. The answer is 202 with `id`,
  `accepted` (recipient count) and `suppressed` (addresses dropped).
- SMTP contract: listeners on 587 and 2525 with STARTTLS required before AUTH, 465 with implicit TLS;
  AUTH PLAIN or LOGIN with user `apikey` and the API key as password; at most 50 RCPT and 10 MB. The
  header `From` must be on a verified Sending domain; the envelope sender is replaced by Nodera's
  return path. The client's Message is kept as written, its headers included, except the ones the
  envelope and the MTA own (`Bcc`, `Return-Path`, the MTA's trace header) and `Feedback-ID`, which
  Nodera sets. Temporary refusals (Daily limit, Package, Pause, suspension) answer 4xx; permanent ones
  (no Package, unverified sender, bad credentials) 5xx.
- Every Message carries a `Message-ID` (the client's if given, in the HTTP `headers` or the SMTP
  Message, else one on the Sending domain), a `Date`, and a `Feedback-ID` naming the Project for
  mailbox providers' feedback tools.
- The MTA is a port: inject one Message for its recipients, each with its own return path, the
  content and its metadata (Project, Message, recipient index, Sending domain); the MTA fetches the
  Sending domain's active key and selector from the mail service. The return path is
  `b+<message id>.<recipient index>.<tag>@n<token>.<domain>`, so an asynchronous bounce maps back to
  its recipient even from a forwarded address; the tag, a MAC keyed by Nodera, keeps whoever has seen
  one return path from forging a bounce or a complaint for another recipient. The KumoMTA adapter calls KumoMTA's HTTP injection API with a shared secret; a fake
  records injections for tests.

### KumoMTA

- The policy is part of the repository: an HTTP injection listener reachable only by the mail
  service, DKIM signing with the Sending domain's active key fetched from mail's internal API and
  cached, the Project as the tenant, one shared egress pool from configuration with the community
  traffic-shaping rules, an inbound listener for the return-path domain that logs asynchronous
  bounces and ARF feedback reports, and a log hook that posts every outcome to mail's internal API.
- In development KumoMTA routes all mail to the compose mail catcher instead of real MX hosts.

### Message events, Suppressions and logs

- Mail's internal API takes KumoMTA's log records: Delivery → `delivered`, TransientFailure →
  `deferred`, Bounce, Expiration and asynchronous bounces → `bounced` (hard when permanent), Feedback
  → `complained`; reception records are ignored. A record is applied once: it is identified by
  Message, recipient, type and time.
- A hard bounce or a complaint adds the address to the Project's Suppressions with its reason and the
  Message it came from. Developers may delete bounce Suppressions; deleting a complaint one is refused
  (409); the operator can.
- Logs: Messages are listed newest first with cursor paging and filters (recipient status, recipient,
  sender, tag, date within 30 days); the detail adds each recipient's status and its Message events
  with the server's answer. A job deletes Messages, recipients, Message events, spool rows and Webhook
  deliveries older than 30 days.

### Daily limit, rates and Pause

- A Project starts at a Daily limit of 200. After each UTC day, the limit doubles when that day the
  Project sent at least half its limit with a bounce rate under 2% and a complaint rate under 0.05%;
  otherwise it stays. The Package's remaining allowance always caps it at send time.
- Every 15 minutes, for Projects with at least 500 emails over the last seven days: hard-bounce
  rate ≥ 5% or complaint rate ≥ 0.1% Pauses the Project (`MailSendingPaused`, with the reason as a
  code and both rates); ≥ 2% or ≥ 0.05% publishes `MailRatesWarning`, at most once a day. Only a
  bounce that proves the address bad counts; an expiry or a content block does not.
- Only an operator lifts a Pause, with `mail unpause`; the Admin side will take this over. The rates
  are then judged from the next UTC day, so the days that led to the Pause do not Pause it again.
- Each finished day is decided once; a clean day doubles the Project's limit as it stands, so a day
  sent before the decision about the day before it, or days a stopped worker missed, still count.

### Webhooks

- At most three per Project: an HTTPS URL (HTTP allowed only in development and test), the subset of
  the six Message events it wants, an active flag, and a secret generated by Nodera, shown once and
  stored encrypted like the DKIM keys.
- A delivery job batches up to 100 pending events per Webhook into one POST of a JSON array, signed
  with `Nodera-Signature: t=<unix>,v1=<hex HMAC-SHA256 of "t.body">`, with a 10-second timeout.
  Non-2xx retries after 1, 2, 5, 10 and 30 minutes, then 1, 2, 4 and 8 hours, and is dropped once 24
  hours have passed since the first attempt. Deliveries and their last error are listed for 30 days.
- These retries are database-scheduled attempts to a Team's server, not RabbitMQ redeliveries, so the
  rule that workers never retry a message is untouched.
- The target host is resolved before each attempt and refused when it is loopback, private, link-local
  or otherwise non-public, outside development and test.

### Events and live updates

- To billing: `MailPackageStarted`, `MailPackageStopped`.
- To notification: `MailDomainVerified`, `MailDomainUnverified`, `MailPackageNearLimit`,
  `MailPackageExhausted`, `MailRatesWarning`, `MailSendingPaused`, each with the Team's and the
  Project's ids, the Project's name and the thing's own fields (domain; Package, allowance and used;
  rates; reason code). Never a recipient list (ADR-0008).
- Realtime (ADR-0007), to the Team with `mail.read`: `mail.domain_changed` and
  `mail.sending_changed`; the web app refetches.
- All through the outbox after commit, routing keys on the common exchange, queues prefixed `mail.`.

### API keys (customer context)

- A new aggregate: a key belongs to a Project of the Team, has a name, a public prefix, the SHA-256
  hash of its secret, its Permissions, its creator and creation time, and its revocation time. At most
  20 active keys per Project.
- The key reads `nd_<id>.<secret>`: the id is random and public, the secret 32 random bytes,
  base62-encoded. Only the hash is stored; the whole key is answered once, on creation.
- Routes under the customer target, all requiring `apikey.write`:
  `GET|POST /v1/teams/:teamID/projects/:projectID/api-keys` and
  `DELETE /v1/teams/:teamID/projects/:projectID/api-keys/:keyID`. The requested Permissions must be
  among those a key may carry (`mail.send` today), and each must be held by the creator's Role.
- Redis wire contracts (ADR-0010): `api_key:<id>` holds the hash, Project, Team and Permissions,
  written on creation and deleted on revocation; `api_key_last_used:<id>` is written by whoever
  authenticates the key and read when keys are listed. The command `sync-api-keys` rewrites every
  active key from the database.
- A member's removal leaves their keys working.

### The integration gateway

- A new binary over the gateway's existing route-table package. Its table, one file per environment,
  lists the upstream services with their routes; a request's service is found by its path alone, and
  the table is refused at start-up if two services could match one request.
- Authentication is the API key from `Authorization: Bearer`, checked against Redis in constant time;
  a route's `permissions` are checked against the key's. Per-key limit of 100 requests a second
  (Redis sliding window), 15 MB bodies, no CORS, health endpoint, correlation ids.
- The request is forwarded unchanged; the mail service checks the key again.
- First route: `POST /v1/mail/messages` → `mail`, requiring `mail.send`. The path is namespaced by
  product because Droplets will share this gateway.

### Billing

- Consumes `MailPackageStarted` and `MailPackageStopped` into intervals per Project.
- Invoice lines become product-neutral: a kind (`droplet`, `mail`) with the droplet columns kept for
  Droplet lines and the Project, its name and the Package code for Mail lines; the PDF shows
  "Mail · <Project> · <Package>", and the DTO carries the kind, the Project and the Package for the
  web app to word the same way.
- The draft of a Period charges, per Project, the highest price among the intervals overlapping it,
  minus what earlier Invoices of the same Period already charged for that Project; nothing when that
  is zero. Threshold totals include Mail lines; tax applies as to Droplet lines.

### Notification

- Six Notification types, in-app and email, for the members holding `mail.read`:
  `mail_domain_verified`, `mail_domain_unverified`, `mail_package_near_limit`,
  `mail_package_exhausted`, `mail_rates_warning`, `mail_paused`. Params carry ids, names, numbers and
  reason codes; the in-app text is the web app's, the email templates exist in `tr` and `en`.

### Permissions

- `pkg/authz` gains `mail.read`, `mail.write`, `mail.send` and `apikey.write`. owner: all;
  developer: adds all four; finance: adds `mail.read`. The set of Permissions an API key may carry is
  declared there too: `mail.send`.
- The web app's copy of the matrix gets the same change.

### Management API (mail service, gateway target `mail`)

- `GET /v1/mail/packages`
- `GET /v1/projects/:projectID/mail` (overview: Package, Period usage, Daily limit, seven-day rates,
  Pause, Billing status)
- `PUT /v1/projects/:projectID/mail/package` (choose, change or cancel)

  `POST …/domains/:domainID/verify`
- `GET /v1/projects/:projectID/mail/messages`, `GET …/messages/:messageID`
- `GET /v1/projects/:projectID/mail/suppressions`, `DELETE …/suppressions/:suppressionID`
- `GET|POST /v1/projects/:projectID/mail/webhooks`, `PUT|DELETE …/webhooks/:webhookID`,

Reads need `mail.read`, writes `mail.write`; a stranger gets 404 and a member without the Permission

## Testing Decisions

A good test drives a public interface the way a client does and asserts what the client sees or what
another context receives: the HTTP status and body, the SMTP reply, an outbox document, a fake's
recorded calls, a Webhook receiver's requests. It never inspects handlers or repositories.

Seams, highest first:

1. **Mail integration suite** (new, primary; mirrors the droplet suite): dockertest PostgreSQL,
   Redis and Mongo; the mail server through its management, sending and internal surfaces, and the
   SMTP listener on a real socket with a test certificate; consumers and jobs called directly with a
   controllable clock. At the edges: a fake MTA that records injections, KumoMTA-shaped log records
   posted to the internal API, a fake DNS resolver, and an httptest Webhook receiver. Scenarios cover
   every story above that the mail service owns: domain add, verify, lose and share between
   Projects; HTTP and SMTP sends with their limits, idempotency and refusals; per-recipient counting;
   Package choice, upgrade, downgrade, cancellation and rollover; Daily limit growth; Suppressions;
   rates, warnings and Pause; Billing status reactions; log expiry; Webhooks with signatures and
   retries; access for owner, developer, finance and strangers; revoked keys.
2. **Customer suite** (existing): API key creation, listing, revocation, Permission ceilings, Redis
   entries, keys surviving a member's removal, `ProjectCreated` carrying the name.
3. **Integration gateway suite** (new, mirrors the customer gateway's): unlisted routes, key
   authentication against Redis, revoked keys, Permission checks, per-key rate limit, body limit.
4. **Customer gateway suite** (existing): the `mail` target's routes and the API key routes'
   Permissions.
5. **Billing suite** (existing): Mail intervals to one line per Project and Period at the highest
   price, the Threshold difference, no charge after day 21, Droplet lines unchanged.
6. **Notification suite** (existing): the six types reach `mail.read` holders, finance included,
   in-app and by email in both languages.
7. **KumoMTA contract test** (new, opt-in by environment variable like the Provider contract test):
   a real KumoMTA container with the repository's policy, the real adapter, a local SMTP sink; the
   DKIM signature verifies with the Project's key and the log hook reaches the internal API.

Unit tests, table-driven where the input is a matrix: Daily limit progression, rate and Pause
evaluation, the highest-price-in-Period rule, recipient counting, record names and DKIM TXT
generation, Webhook signing, SMTP reply mapping, domain normalization, the backoff schedule.

Prior art: the droplet suite (fake Provider, jobs called directly, outbox assertions), the billing
suite (controllable clock), the customer gateway suite, the notification suite, the Provider contract
test. The web app has no automated UI tests; type-check, lint and build guard it.
